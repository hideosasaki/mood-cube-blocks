# 要件定義

このリポジトリ (MakeCode 拡張機能) の要件を定義する。本ファイルがこのプロジェクトの source of truth。


## 背景

このリポジトリは「mood cube」という個人のフィジェット作品のために作られた MakeCode 拡張機能。動画提出型の応募作品の一環として開発しているが、コンテスト固有の事情 (締切・部門・審査軸) は拡張機能の設計には影響しないため要件には含めない。

### 作品の構成

mood cube は触り心地と力の発散の対をなす 2 つのキューブで構成される。両キューブで同じ micro:bit を使いつつ、主役となるセンサが異なる (触感は加速度センサ、握りつぶしは圧力センサ)。フィジェットとして「触れて落ち着く」方向と「握って発散する」方向の双方を提供する。

#### 触感キューブ

透明アクリルキューブ (約 6cm 角) の 6 面にそれぞれ異なる触感の素材を貼り、ピンを刺して触感を楽しむ。内部に micro:bit と NeoPixel を仕込み、上を向いた面に応じて発光や振動で反応する。静的・受動的な体験を担う。

#### 握りつぶしキューブ

柔らかい外装 (布製お手玉式、約 6cm 角) の中に micro:bit と圧力センサを仕込み、握りしめる強さに応じて発光や振動が変化する。動的・能動的な体験を担う。

### このリポジトリの位置づけ

mood cube はハードウェアの組み立てと、micro:bit 上で動く挙動ロジックの 2 層で成り立つ。本リポジトリは後者のうちハードウェアに近い層だけを提供する。

責務は次のように分離する。ハードウェアや較正値が変わってもアプリ層のブロックは原則そのまま動く。逆に、アプリ層を作り変えても拡張側は触らない。

#### 拡張機能 (このリポジトリ)

親が Static TypeScript で実装。配線・センサ較正・タイミング・ハードウェアの抽象化を担う。

#### アプリ層 (このリポジトリの外)

子供が MakeCode のブロック UI で組む。どの入力で何を光らせるか、どんな体験を作るかを決める。

## このリポジトリのスコープ

### 含めるもの

ハードウェアに依存する入出力を MakeCode ブロックとして抽象化する。具体的な機能カテゴリは次のとおり。各カテゴリの詳細要件は後続の節で定義する。

- 触感キューブの上面判定
- 触感キューブのピン刺し検知
- 握りつぶしキューブの圧力読み取り
- NeoPixel による発光制御
- バイブによる振動制御

### 含めないもの

アプリ層 (体験のデザイン・意味付け・モード切替などのロジック) はこのリポジトリに含めない。詳細は「アプリ層に委ねるもの」の節で定義する。

### micro:bit 標準ブロックの扱い

LED 5x5、ボタン A/B、ロゴタッチ、磁気センサ、ラジオなど、micro:bit 標準ブロックで素直に扱えるものはこの拡張でラップしない。アプリ層が標準ブロックを直接使う前提とする。

## 対象ハードウェア

要件定義はインターフェイス粒度で書く。具体的な部品型番・個数・抵抗値・配線処理などは実装側で決める。

### micro:bit のバージョン

v2 限定。v1 互換は維持しない。

### ピン使途

両キューブ共通で次のピン割当を前提とする。

- P0: 触感キューブではピン刺し検知 (デジタル入力、6 面並列、内蔵プルアップ)。握りつぶしキューブでは圧力センサのアナログ入力
- P1: バイブ駆動 (PWM 出力)
- P2: PL9823 のデータライン

### 発光素子

PL9823 (NeoPixel 互換のフルカラー LED IC) を各キューブに 1 個搭載する。プロトコルは NeoPixel と同じなので MakeCode の neopixel ライブラリで駆動できる。

### バイブ

振動モーターを各キューブに 1 個搭載し、P1 から PWM で駆動する。micro:bit GPIO の出力電流では直接駆動できないため外部駆動回路を介する前提とする。回路の詳細は実装側で決める。

### 触感キューブの入力部

6 面に導電層を配置し、すべて並列に P0 へ接続する。ピン (GND テザー) が導電層に触れると P0 が LOW になる。どの面に刺さったかは micro:bit 内蔵の加速度センサで上面を判定して特定する。

### 握りつぶしキューブの入力部

圧力に応じて抵抗値が変化する素子を分圧回路で P0 のアナログ入力に接続する。素子の候補は LCX-300 で、銅箔電極のサンドイッチ構造を想定している。

## 触感キューブの要件

### 上面判定

加速度センサから「いま上を向いている面」を 6 面のいずれかとして返す。回転中など上面が定まらない期間は判定を保留し、安定して特定できたときに値を更新する。アプリ層から見ると上面値は常に 6 面のいずれかであり、不定状態は API に出さない。

提供形式はポーリングとイベントの両方とする。

- ポーリング: 現在の上面値をいつでも取得できる
- イベント: 上面が変化したとき (前回の安定値と異なる面で安定したとき) に発火する

### ピン刺し検知

P0 の状態と上面判定を統合し、上面の面に対するピン刺しイベントだけをアプリ層に通知する。生の P0 状態は公開しない。

イベントは「ピンが刺さった瞬間」と「ピンが抜けた瞬間」の両方を提供する。どちらのイベントも、その瞬間に上を向いていた面を引数として伴う。

判定の方針:

- イベントはエッジ駆動とする。P0 の LOW→HIGH 遷移の瞬間に「抜けた」、HIGH→LOW の瞬間に「刺さった」を発火する
- 上面に紐づくのはエッジの瞬間のみ。ピンが刺さったままキューブを回転させても再発火しない
- 拡張側でデバウンス処理を済ませた上でアプリ層にイベントを渡す。子供がチャタリング対策を意識せずに済むようにする

## 握りつぶしキューブの要件

### 圧力読み取り

圧力センサから握りの強さを 0-9 の整数値として返す。

正規化は固定マッピングで実装する。実装時に決めた抵抗値の範囲を 0-9 に割り振り、アプリ層に見せるキャリブレーション機構 (キャリブ操作ブロック・起動時の操作要求) は持たない。ただし無握り baseline の補正は拡張内部で起動時に透明に行ってよい。生 ADC 値はアプリ層に公開せず、拡張内部に閉じる。

提供形式はポーリングのみ。値の連続変化を逐次イベントで通知する形は取らない。

### イベント

ポーリング値の連続変化とは別に、アプリ層が体験を組みやすい区切りとなる瞬間をイベントとして発火する。

- 握り始め: 強さが 0 から 1 以上になった瞬間
- 離した: 強さが 1 以上から 0 になった瞬間
- 最大到達: 強さが 9 に達した瞬間
- 最大解除: 強さが 9 から外れた瞬間

いずれのイベントも拡張側でデバウンス済みとし、ノイズによる微小な値の往復で発火しないようにする。子供がチャタリング対策を意識せずに済むようにする。

## 発光の要件

両キューブ共通の発光 API を提供する。各キューブの PL9823 1 個を制御するシンプルな抽象を、アプリ層に見せる。

### 内部実装の前提

発光制御は Microsoft 公式の `pxt-neopixel` 拡張を内部依存として使い、それをラップする。子供のアプリ層には mood-cube-blocks のブロックだけが見え、`pxt-neopixel` のブロックは直接見せない。これによりピン番号 (P2) と LED の個数 (1) はアプリ層から隠蔽される。

### 色指定

プリセット色のドロップダウンから選ぶブロックを提供する。プリセットの中身は `pxt-neopixel` 標準と同じ 10 色 (Red / Orange / Yellow / Green / Blue / Indigo / Violet / Purple / White / Black) に揃える。RGB 直接指定のブロックは要件には含めない。

### 明度

明度を 0-9 の整数で指定するブロックを提供する。内部で `pxt-neopixel` の 0-255 範囲にマップする。圧力の粒度 (0-9) と揃える。

### 消灯

専用の「消灯」ブロックは作らない。次のいずれの方法でも消灯できる。

- 色を Black に設定する
- 明度を 0 に設定する

### 発光パターン

点滅・フェード・パルスなどの時間変化を伴うパターンは拡張側で持たない。アプリ層が MakeCode の標準的なタイマーやループのブロックで自分で組む。

## 振動の要件

両キューブ共通の振動 API を提供する。各キューブの振動モーター 1 個を P1 の PWM で駆動する。

### 強度

強度を 0-9 の整数で指定する。発光の明度や握りの強さと粒度を揃える。

### 同期と非同期

ユースケースに応じて 2 種類のブロックを提供する。

- 同期: 強度と時間 (ms) を指定して鳴らし、指定時間が経つと止まる。実行中はブロックする。短い単発の演出に使う
- 非同期: 強度を指定して鳴らし始め、別ブロックで明示的に止めるまで鳴り続ける。握り中ずっと鳴らすような継続演出や、強度を逐次変えたい場合に使う

### 連続パターン

カウントダウン的な振動の加速・パルスのような時間変化を伴うパターンは拡張側で持たない。アプリ層が MakeCode の標準的なタイマーやループのブロックで自分で組む。発光と同じ方針。

### 駆動回路

micro:bit GPIO の出力電流では振動モーターを直接駆動できないため、外部の駆動回路を介する前提とする。回路の詳細は実装側で決めるため要件には書かない。

## ペア間連動の要件

触感キューブと握りつぶしキューブはペアで使うので、片方のキューブの入力状態がもう片方のキューブのコードからも扱えるようにする。これにより「相手のキューブの状態に自分のキューブが反応する」体験をアプリ層で組める。

### キューブの役

各 micro:bit のコードは自分が触感キューブとして動くのか、握りつぶしキューブとして動くのかをアプリ層が起動時に宣言する。`cubePair` の役宣言ブロックを呼ぶ。

役を宣言しないとペア連動 (相手側のイベント受信・相手側の値取得) は無効になる。ただし単独キューブとしての動作 (自分のセンサのイベントとポーリング、ローカルな発光と振動) は役の宣言に関係なく動く。

### API は透明

`cubeTouch` のイベントとポーリングは触感キューブ側のハードウェアからしか発生せず、`cubeGrip` のイベントとポーリングは握りつぶしキューブ側のハードウェアからしか発生しない。各情報源が世の中に 1 つずつしか存在しないため、アプリ層側でローカルから来たかペア越しに来たかを区別する必要がない。

たとえば握りつぶしキューブのコードで `cubeTouch.onPinStuck` を書くと、相棒の触感キューブにピンが刺さったときに自分の handler が動く。同じコードを触感キューブで書けば、自分のキューブのピン刺しに反応する。get 系も同様で、握りつぶしキューブのコードで `cubeTouch.surface()` を呼ぶと相棒の現在の上面値が返り、触感キューブで呼べば自分の値が返る。

### 入力イベントは自動配信

cubeTouch と cubeGrip が公開する入力イベント (ピン刺し・上面変化・握り始め・離した・最大到達・最大解除) は、発生時に拡張内部でペアにブロードキャストする。受信側でも同じイベントとして発火する。

イベント自動配信は発火頻度が低く (回転や握りの節目だけ)、電池消費が小さい。

### ポーリング値はリクエスト・レスポンス

相手側のポーリング値 (上面の現在値、握りの現在強度) は、アプリ層が取得ブロックを呼んだそのタイミングで内部的に相手にリクエストを送信し、応答を待って値を返す。同期呼び出しでラウンドトリップを伴う。

一定時間 (実装側で決める短いタイムアウト) 内に応答がなければデフォルト値 (Face 0・強度 0 など) を返す。

この方式は「アプリ層が呼んだ瞬間だけ通信する」ため省電力。常時ブロードキャストにせず、必要なときだけ取りに行く。子供にはレイテンシ (数十 ms 程度) があることだけ注記する。`forever` ループ内で毎フレーム呼ぶような使い方は推奨しない。

### 出力は自分のキューブにのみ作用

cubeLight と cubeVibe の出力メソッドは伝搬しない。`cubeLight.setColor(Red)` を呼んでも光るのは自分のキューブだけ。

設計の原則として、各キューブのコードは「自分のキューブが何をするか」だけを書く。相手のキューブを直接操作する手段は提供しない。代わりに「相手で起きたことを受け取って自分のキューブを操作する」形でアプリ層を組む。

たとえば「相手の握り最大到達に反応して自分のキューブを赤く光らせる」を実現するには、触感キューブ側のコードに `cubeGrip.onMaxReached` で `cubeLight.setColor(Red)` を呼ぶ形で書く。「自分の握り最大到達で相手を光らせる」という発想ではなく、「相手の握り最大到達を受けて自分を光らせる」という発想になる。

### 通信路の隠蔽

内部実装は micro:bit のラジオ機能を使うが、ラジオの存在はアプリ層から見えない。子供はラジオ送受信ブロックや受信メッセージの型を意識する必要がない。

### ペアグループ ID

複数のペアが同じ場で動くと混信するため、ペアごとに通信を分ける論理グループ ID をアプリ層が設定できるようにする。`cubePair` namespace にグループ ID 設定ブロックを提供する。両キューブのコードで同じ ID を設定すれば連動が成立する。

拡張は妥当なデフォルト値を 1 つ持つ。子供が ID の存在を意識しなくても通常運用 (1 ペアだけの環境) では動く。混信回避が必要な場合のみ ID 設定ブロックを使う。

ID をどう運用するか (起動時に固定値を書く・ボタンで増減して現地で切り替える・ジェスチャーで切り替える等) はアプリ層の責務とする。

## キューブ間の共通化方針

出力 (発光・振動) は両キューブで完全共通、入力 (上面判定・ピン刺し・圧力) はキューブ固有とする対称構造を取る。

### 出力は共通 namespace

発光と振動の API は 1 つの共通 namespace に置く。アプリ層は「どのキューブで動いているか」を意識せず、ただ「光らせる」「鳴らす」と書ける。1 個の micro:bit にロードされたコードはどちらか片方のキューブの役を担い、その上で共通 API が呼ばれる。

### 入力はハードウェア種別ごとに namespace を分ける

触感キューブのハードに紐づく入力ブロック (上面判定・ピン刺し) と、握りつぶしキューブのハードに紐づく入力ブロック (圧力読み取り・関連イベント) は別の namespace に分ける。アプリ層から見て「どのハードウェアから来た入力か」を区別しやすくするため。透明 API のもとでは、自分のキューブ・相棒のキューブの区別ではなく、ハードウェア種別の区別が分割軸になる。

### namespace は 5 つ

以上から namespace は 5 つになる。出力共通は発光と振動で更に分け、ペア連動の制御用を別途設ける。

- 触感キューブの入力用 namespace
- 握りつぶしキューブの入力用 namespace
- 発光の共通 namespace
- 振動の共通 namespace
- ペア連動の制御用 namespace

各 namespace の具体的な名前は次の節で決める。

## namespace 構成

5 つの namespace で構成する。共通プリフィックス `cube` を全 namespace に付け、子供がブロックパレット上でこの拡張のブロックをひとまとまりとして認識できるようにする。

| 用途 | namespace | 色 | アイコン (Font Awesome) |
| --- | --- | --- | --- |
| 触感キューブの入力 | `cubeTouch` | `#FF8C42` (オレンジ) | `` (`fa-hand-pointer-o`) |
| 握りつぶしキューブの入力 | `cubeGrip` | `#E63946` (赤) | `` (`fa-hand-rock-o`) |
| 発光 (共通) | `cubeLight` | `#FFD23F` (黄) | `` (`fa-lightbulb-o`) |
| 振動 (共通) | `cubeVibe` | `#6A4C93` (紫) | `` (`fa-bell`) |
| ペア連動の制御 | `cubePair` | `#2A9D8F` (青緑) | `` (`fa-link`) |

色相を散らして 5 namespace を視覚的に区別できるようにする。`mood` のような意味付け語は採用せず、ハードウェア役割をそのまま名前にする。

## アプリ層に委ねるもの

この拡張はハードウェア入出力の薄いラップに徹し、体験デザインはアプリ層に委ねる。アプリ層が担う領域は次のとおり。

- 意味付け: 色とユースケースの対応 (例: ある色を「集中」「不安」のような状態と紐付ける) や、面の意味付け (例: どの面が何を表すか) はアプリ層が決める。拡張は色や面番号といったハードウェア上の値だけを扱う
- 体験デザイン: モード切替・ステートマシン・タイマー駆動の演出 (発光パターン・振動パターン・カウントダウン等) はアプリ層が標準ブロックで組む
- 入力と出力の結びつけ: どの入力イベントで何を光らせるか、何を鳴らすかはアプリ層が定義する
- キューブの役の宣言 (必須): 起動時に `cubePair` の役宣言ブロックで自分のキューブが触感か握りつぶしかを必ず指定する。これを呼ばないとペア連動は無効になる
- ペアグループ ID の運用 (任意): デフォルト値で 1 ペアだけの環境は動く。混信回避が必要な場合のみ ID 設定ブロックを使う。起動時に固定値を書くか、ボタンで切り替えられるようにするかはアプリ層が決める

各機能ごとに拡張が公開しない内部状態 (上面判定の不定状態、生 ADC 値、生 P0 状態など) は各節で個別に述べた。
