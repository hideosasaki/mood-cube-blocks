# 要件定義

このリポジトリ (MakeCode 拡張機能) の要件を定義する。本ファイルがこのプロジェクトの source of truth。

## スコープ

### 含めるもの

ハードウェアに依存する入出力をMakeCodeブロックとして抽象化する。具体的な機能カテゴリは次のとおり。各カテゴリの詳細要件は後続の節で定義する。

- 触感キューブの上面判定
- 触感キューブのピン刺し検知
- 握りキューブの圧力読み取り
- NeoPixelによる発光制御
- バイブによる振動制御
- ペア間の入力連動 (内部でラジオを使うが、その存在は隠蔽する)
- 電力管理 (自動 deepSleep。アプリ層にAPIは公開しない)

### 含めないもの

- アプリ層 (体験のデザイン・意味付け・モード切替などのロジック)
- micro:bit 標準ブロックで素直に扱えるもの (LED 5x5、ボタンA/B、ロゴタッチ、磁気センサ、ラジオ) のラップ
- micro:bit v1 互換性

### アプリ層に委ねるもの

この拡張はハードウェア入出力の薄いラップに徹し、体験デザインはアプリ層に委ねる。アプリ層が担う領域は次のとおり。

- 意味付け: 色とユースケースの対応 (例: ある色を「集中」「不安」のような状態と紐付ける) や、面の意味付け (例: どの面が何を表すか) はアプリ層が決める。拡張は色や面番号といったハードウェア上の値だけを扱う
- 体験デザイン: モード切替・ステートマシン・タイマー駆動の演出 (発光パターン・振動パターン・カウントダウン等) はアプリ層が標準ブロックで組む
- 入力と出力の結びつけ: どの入力イベントで何を光らせるか、何を鳴らすかはアプリ層が定義する
- キューブの役の宣言 (必須): 起動時に`cubePair`の役宣言ブロックで自分が触感か握りかを必ず指定する。これを呼ばないとペア連動は無効になる
- ペアグループIDの運用 (任意): デフォルト値で1ペアだけの環境は動く。混信回避が必要な場合のみID設定ブロックを使う。起動時に固定値を書くか・ボタンで切り替えるかはアプリ層が決める
- 連続出力の自制: 3分以上の連続発光・連続振動を行わない。拡張は3分アイドルで強制 deepSleep に入り、LEDとvibeをオフにする

各機能ごとに拡張が公開しない内部状態 (上面判定の不定状態、生 ADC 値、生 P0 状態など) は各節で個別に述べる。

## 対象ハードウェア

要件定義はインターフェイス粒度で書く。具体的な部品型番・個数・抵抗値・配線処理などは実装側で決める。

### micro:bit のバージョン

v2 限定。v1 互換は維持しない。

### ピン使途

両キューブ共通で次のピン割当を前提とする。

- P0: 触感キューブではピン刺し検知 (アナログ振幅検出、6面並列+動作点を定める弱いプルアップ)。握りキューブでは圧力センサのアナログ入力
- P1: バイブ駆動 (PWM 出力)
- P2: PL9823 のデータライン

### 発光素子

PL9823 (NeoPixel 互換のフルカラー LED IC) を各キューブに1個搭載する。プロトコルは NeoPixel と同じなので MakeCode の neopixel ライブラリで駆動できる。

### バイブ

振動モーターを各キューブに1個搭載し、P1 から PWM で駆動する。micro:bit GPIO の出力電流では直接駆動できないため外部駆動回路を介する前提とする。回路の詳細は実装側で決める。

### 触感キューブの入力部

6面に導電層を配置し、すべて並列に P0 へ接続する。ピンは独立した金属体で、ケーブルでキューブと繋がない。P0 は数百kΩ級の弱いプルアップで 3V に吊り、非タッチ時の動作点を固定する (抵抗値は実測で決めて実装側が持つ)。

検出の電気的経路は人体を介した分圧とする。触感素材を固定する金属ボルトを外装に露出させて GND に接続し、キューブを持つ手の接触点とする。人がピンを握って導電層に触れると、ボルト (GND) →人体→ピン→導電層 (P0) の経路ができ、人体抵抗と P0 プルアップの分圧で電位が下がる。この低下を ADC で検出する。人体が直接 GND に触れる構成のため、電池駆動 (接地から浮いた状態) でも成立する。持つ手がボルトに触れていることが検出の前提条件となるため、自然な持ち方で指が掛かるボルト配置にする。

micro:bit v2 の容量タッチ (MakeCode ランタイムのタッチ検出) は使わない。ランタイムの容量タッチは小電極を前提とした全ピン共用スキャナで、6面並列の大電極では検出が成立しないことを実測で確認した (2026-07-06、docs/measurements)。また、環境ノイズの結合だけに頼る検出も採らない。USB 接続 (接地あり) では成立するが電池駆動では信号が消えることを実機で確認した。

導電層は触感素材 (スポンジ等) で覆われ、素手では届かずピンだけが貫通する構造を前提とする。触感素材は絶縁性であること。導電性の素材は素手で持っただけでピン刺しと同一の信号になるため使えない (実測で確認)。金属ボルトは触感素材のみを固定し、導電層には触れさせない (触れると P0 が GND に直結して検知が死ぬ。組み立て時に面ごとに絶縁を確認する)。導電層は接着等でボルトと独立に固定し、P0 への配線は内部の圧着端子で機械的に接続する。

電気的には6面が並列なのでどの面が刺されたかは区別できない。ピンが刺された事実と、その瞬間に内蔵加速度センサが判定した上面値を、組として通知する。「上面に刺された」かどうかを測定しているのではなく、「ピン刺しが起きた瞬間の姿勢」を返している。アプリ層は姿勢情報を使うかどうかを自由に選べる。

### 握りキューブの入力部

圧力に応じて抵抗値が変化する素子を分圧回路で P0 のアナログ入力に接続する。素子はIC保護などに使用する導電スポンジ LCX-300 で、アルミ箔電極のサンドイッチ構造を想定している。

P0 へのオーディオ出力ミラーの無効化 (ピン刺し検知の節を参照) は握りキューブでも必要になる。音を鳴らすと P0 がオーディオ出力に切り替わり、圧力の ADC 読みが壊れるため。拡張は役の設定時に両キューブ共通で無効化する。

## 触感キューブの要件

### 上面判定

加速度センサから「いま上を向いている面」を6面のいずれかとして返す。回転中など上面が定まらない期間は判定を保留し、安定して特定できたときに値を更新する。アプリ層から見ると上面値は常に6面のいずれかであり、不定状態はAPIに出さない。

提供形式はポーリングとイベントの両方とする。

- ポーリング: 現在の上面値をいつでも取得できる
- イベント: 上面が変化したとき (前回の安定値と異なる面で安定したとき) に発火する

### ピン刺し検知

P0 のアナログ振幅からピン刺しの瞬間を検出し、アプリ層に通知する。生の P0 状態 (ADC 値・baseline・しきい値) は公開しない。

提供形式はイベントのみとする。

- イベント: 「ピンを刺した瞬間」に刺すたび毎回発火する。その瞬間に上を向いていた面を引数として伴う
- 「抜けた」イベントと「刺さっているか」のポーリングは提供しない。人体経由の信号は保持中に数十秒で減衰するため刺さり状態を電気的に維持できず (2026-07-06 実測)、状態遷移モデルでは連打 (素早い抜き差し) の2打目以降が抜け確定待ちで1秒以上出てこないことを実機で確認した (2026-07-12)。体験の核を「刺した瞬間」の即時フィードバックに置き、状態は持たない

判定の方針:

- 面引数は検出瞬間に判定された上面の snapshot を渡す。刺したままキューブを回転させても再発火しない
- 判定は拡張が自前で行う。アクティブ中は 50ms 周期で P0 をサンプリングする
- ゆっくり追従する参照値 (指数移動平均) を持ち、サンプルが参照値から大きく下に外れた最初の1サンプルで即発火する。検出遅延は実質サンプリング1周期 (50ms)
- 連発の抑止は不応期ではなく再アーム方式。発火後は「参照値近傍のクリーンなサンプルが一定時間連続する」まで次の発火を封じる。刺している間の商用ノイズの揺れではクリーン連続が成立せず再発火しない。抜いて次を刺す動作では抜いている間に自然に再アームされる (連打の実測波形で1打ごとの発火を確認、2026-07-12)
- 参照値は個体差 (漏れ電流による動作点の違い)・基板差・温度変化も自動で吸収するため、起動時やスリープ前の較正を持たない。下振れ中は参照値を凍結し、信号に引き寄せられて感度が落ちるのを防ぐ
- しきい値・再アーム時間などの具体値は実装定数とし、根拠データは docs/measurements に置く (2026-07-12-poke.json ほか)

既知の限界として受容するもの:

- 接触が浅い面 (メッシュとフォークの接触不良) では、刺しっぱなしの間も信号が刺し直しと区別できない形で揺れ、「刺した」が連発することがある (2026-07-12 実測)。接触の物理改善で解消する種類の問題で、判定側では対処しない
- 刺したまま保持して信号がベースラインへ減衰し切った後に再び深く落ちると、刺し直しとして発火する
- 1サンプル判定のため、実測記録にない種類の単発ノイズスパイクには誤発火しうる。問題が観測されたら再検討する
- フォークを持ちっぱなしで素早い抜き差しを繰り返すと刺すたびに振幅が減衰し、取りこぼすことがある (2026-07-06 実測)
- 拡張は初期化時に P0 へのオーディオ出力ミラーを無効化する。micro:bit v2 は音を鳴らすと P0 がオーディオ出力に切り替わり、以降のピン刺し検知が失われるため。この無効化により、アプリ層は音ブロックを自由に使ってよい

### 手に取る/置く

触感キューブを手に取った瞬間と、置いて静止した瞬間をイベントとして発火する。電力管理で定義する動き検知プリミティブを共有して判定する。

- `onPickUp`: 静止状態から動きが検出されたエッジで即時発火
- `onPutDown`: 動き状態から静止が一定時間 (実装で決める。1〜2秒目安) 続いたエッジで発火

机を叩いた振動などによる単発の誤発火は許容する (deepSleep からの起床と同じ方針)。

## 握りキューブの要件

### 圧力読み取り

圧力センサから握りの強さを 0-9 の整数値として返す。

正規化は固定マッピングで実装する。実装時に決めた抵抗値の範囲を 0-9 に割り振り、アプリ層に見せるキャリブレーション機構 (キャリブ操作ブロック・起動時の操作要求) は持たない。ただし無握り baseline の補正は拡張内部で透明に行ってよい。生 ADC 値はアプリ層に公開せず、拡張内部に閉じる。

baseline 補正はスリープに入る直前に行う。起動時は手に持っている可能性が高いのに対し、スリープ直前は無操作が続いた後なので無握りがほぼ確実なため。ドリフトで幽霊値 (無握りなのに強さ ≥ 1) が出た個体も、放置されれば必ずスリープに到達して校正される。校正は複数サンプルの中央値 + マージンを baseline にし、ばらつきが大きい場合や値が高すぎる (握られている疑い) 場合は現在値を維持する。最初のスリープまではデフォルト値で動く。

ポーリングで現在の強さを取得できる。

### イベント

アプリ層が体験を組みやすい区切りとなる瞬間をイベントとして発火する。

- 握り始め: 強さが0から1以上になった瞬間
- 離した: 強さが1以上から0になった瞬間
- 最大到達: 強さが9に達した瞬間
- 最大解除: 強さが9から外れた瞬間
- 強さ変化: 強さの整数値 (0-9) が変わった瞬間。ハンドラには新しい強さが渡る

いずれのイベントも拡張側でデバウンス済みとし、ノイズによる微小な値の往復で発火しないようにする。子供がチャタリング対策を意識せずに済むようにする。強さ変化イベントの発火頻度は実用上 5回/秒未満を想定する (ヒステリシスにより細かい往復は抑制される)。

### 手に取る/置く

握りキューブを手に取った瞬間と、置いて静止した瞬間をイベントとして発火する。判定方針と仕様は触感キューブの「手に取る/置く」と同じ (動き検知プリミティブを共有)。

- `onPickUp`: 静止状態から動きが検出されたエッジで即時発火
- `onPutDown`: 動き状態から静止が一定時間続いたエッジで発火

## 発光の要件

両キューブ共通の発光 API を提供する。各キューブの PL9823 1個を制御するシンプルな抽象を、アプリ層に見せる。

### 内部実装の前提

発光制御は Microsoft 公式の `pxt-neopixel` 拡張を内部依存として使い、それをラップする。子供のアプリ層には mood-cube-blocks のブロックだけが見え、`pxt-neopixel` のブロックは直接見せない。これによりピン番号 (P2) と LED の個数 (1) はアプリ層から隠蔽される。

### 色指定

プリセット色のドロップダウンから選ぶブロックを提供する。プリセットの中身は `pxt-neopixel` 標準と同じ10色 (Red / Orange / Yellow / Green / Blue / Indigo / Violet / Purple / White / Black) に揃える。RGB 直接指定のブロックは要件には含めない。

### 明度

明度を 0-9 の整数で指定するブロックを提供する。内部で `pxt-neopixel` の 0-255 範囲にマップする。圧力の粒度 (0-9) と揃える。

### 消灯

専用の「消灯」ブロックは作らない。次のいずれの方法でも消灯できる。

- 色を Black に設定する
- 明度を0に設定する

### 起動時の初期化

PL9823 は電源投入直後の出力が不定で、起動瞬間に意図しない色が一瞬出ることがある。拡張のロード時に Black を一度送って物理 LED を確実に消灯状態にする。アプリ層が起動直後に `setColor` を呼ぶ場合は、その色で素直に上書きされる。

### 発光パターン

点滅・フェード・パルスなどの時間変化を伴うパターンは拡張側で持たない。アプリ層が MakeCode の標準的なタイマーやループのブロックで自分で組む。

## 振動の要件

両キューブ共通の振動 API を提供する。各キューブの振動モーター1個を P1 の PWM で駆動する。

### 強度

強度を 0-9 の整数で指定する。発光の明度や握りの強さと粒度を揃える。

### 同期と非同期

ユースケースに応じて2種類のブロックを提供する。

- 同期: 強度と時間 (ms) を指定して鳴らし、指定時間が経つと止まる。実行中はブロックする。短い単発の演出に使う
- 非同期: 強度を指定して鳴らし始め、別ブロックで明示的に止めるまで鳴り続ける。握り中ずっと鳴らすような継続演出や、強度を逐次変えたい場合に使う

### 連続パターン

カウントダウン的な振動の加速・パルスのような時間変化を伴うパターンは拡張側で持たない。アプリ層が MakeCode の標準的なタイマーやループのブロックで自分で組む。発光と同じ方針。

## ペア間連動の要件

触感キューブと握りキューブはペアで使うので、片方のキューブの入力状態がもう片方のキューブのコードからも扱えるようにする。これにより「相手のキューブの状態に自分のキューブが反応する」体験をアプリ層で組める。

### 役の宣言

各 micro:bit のコードは自分が触感キューブとして動くのか、握りキューブとして動くのかをアプリ層が起動時に宣言する (`cubePair` の役宣言ブロック)。役を宣言しないとペア連動 (相手側のイベント受信・相手側の値取得) は無効になる。ただし単独キューブとしての動作 (自分のセンサのイベントとポーリング、ローカルな発光と振動) は役の宣言に関係なく動く。

### 振る舞いの方針

API はハードウェア由来であり、ローカル発生かペア越しかの区別をアプリ層に見せない。

- `cubeTouch` のイベントとポーリングは触感キューブ側のハードウェアからしか発生しない。握りキューブのコードで `cubeTouch.onPinStuck` を書くと、相棒の触感キューブにピンが刺さったときに自分のハンドラが動く。`cubeTouch.surface()` を握りキューブで呼ぶと相棒の現在の上面値が返る
- `cubeGrip` も同様で、握りキューブ側のハードウェアからしか発生しない
- `cubeLight` と `cubeVibe` の出力は伝搬しない。`cubeLight.setColor(Red)` を呼んでも光るのは自分のキューブだけ

設計の原則として、各キューブのコードは「自分のキューブが何をするか」だけを書く。相手のキューブを直接操作する手段は提供しない。代わりに「相手で起きたことを受け取って自分のキューブを操作する」形でアプリ層を組む。

たとえば「相手の握り最大到達に反応して自分のキューブを赤く光らせる」を実現するには、触感キューブ側のコードに `cubeGrip.onMaxReached` で `cubeLight.setColor(Red)` を呼ぶ形で書く。「自分の握り最大到達で相手を光らせる」という発想ではなく、「相手の握り最大到達を受けて自分を光らせる」という発想になる。

### 通信方式

内部実装は micro:bit のラジオ機能を使うが、ラジオの存在はアプリ層から見えない。子供はラジオ送受信ブロックや受信メッセージの型を意識する必要がない。

- 入力イベント (ピン刺し・上面変化・握り始め・離した・最大到達・最大解除・強さ変化・手に取る・置く) は発生時に拡張内部でペアにブロードキャストする。受信側でも同じイベントとして発火する。発火頻度が低く電池消費が小さい。Touch 側で握り強さに追従する用途では、`requestStrength` を `forever` で呼ぶよりこのイベントを使うほうが軽い
- ポーリング値 (上面の現在値、握りの現在強度) は、アプリ層が取得ブロックを呼んだそのタイミングで内部的に相手にリクエストを送信し、応答を待って値を返す。同期呼び出しでラウンドトリップを伴う。一定時間 (実装側で決める短いタイムアウト) 内に応答がなければデフォルト値 (Face 1・強度0など) を返す。「アプリ層が呼んだ瞬間だけ通信する」省電力設計。子供にはレイテンシ (数十ms程度) があることだけ注記する。`forever` ループ内で毎フレーム呼ぶような使い方は推奨しない

### ペアグループ ID

複数のペアが同じ場で動くと混信するため、ペアごとに通信を分ける論理グループ ID をアプリ層が設定できるようにする。`cubePair` namespace にグループ ID 設定ブロックを提供する。両キューブのコードで同じ ID を設定すれば連動が成立する。

拡張は妥当なデフォルト値を1つ持つ。子供が ID の存在を意識しなくても通常運用 (1ペアだけの環境) では動く。混信回避が必要な場合のみ ID 設定ブロックを使う。ID をどう運用するか (起動時に固定値を書く・ボタンで増減して現地で切り替える・ジェスチャーで切り替える等) はアプリ層の責務とする。

## 電力管理の要件

単3×3 電池駆動で常時アクティブだと約3日で消耗する。長時間放置時のバッテリー消費を抑えるため、拡張内部で自動的に deepSleep を制御する。アプリ層にはAPIを公開しない (完全に拡張内部の挙動)。

### 設計方針

体験上は「触ると両方反応する」「使わないときは勝手に寝る」という挙動だけが見え、アプリ層のコードに省電力を意識した分岐は一切入らない。両キューブを完全対称に扱い、役による条件分岐も持たない。

### スリープ突入条件

直近3分間、拡張が公開する入力イベントが発火していないときに自動で deepSleep に入る。LED 点灯中・vibe 動作中もスリープの対象とする。アプリ層は3分以上の連続出力を行わない運用を前提とする。

### ハード起床トリガー

両キューブで対称に次を起床トリガーとする。いずれかが発火すると即時起床する。

- ボタンA
- ボタンB

P0 は起床トリガーにしない。触感キューブの6面電極は環境ノイズを常時拾うため、デジタル起床にすると不定起床で電池を消耗する恐れがある。握りキューブの圧力は ADC 入力で割り込み起床できない。P0 由来の起床は次節の周期 wake でのサンプリングが担う。

各キューブでの実用上の挙動は次のとおり。

- 触感キューブ: ピンが刺さった状態を周期 wake が最大1秒で検出して起床する。置いたまま1秒未満で刺して抜いた場合の起床は保証しない (刺す所作の振動を動き検知が拾うことは多いが、保証はしない)
- 握りキューブ: 握った圧力を周期 wake が最大1秒で検出して起床する。手に取る所作の動き検知でも起床する

### 動き検知プリミティブ

加速度センサの3軸それぞれの前回値との差の総和が閾値を超えたかどうかで「動いている」「静止している」を判定する。閾値はひとつ持ち、後述のソフト起床と pickup/putdown 検知の両方で共通に使う。動き検知は「持ち上げた・向きを変えた・振った」を拾う方針とする。握り圧力のような触れ方依存の特殊判定は持たず、両キューブで対称に動作する。

サンプル周期はコンテキストで異なる。

- スリープ中の周期 wake: 1秒に1回サンプル
- アクティブ中: pickup の即応のため細かくサンプル (具体間隔は実装で決める)

### 周期 wake によるソフト起床

両キューブとも1秒周期で短時間 wake し、次を行う。

- 動き検知プリミティブで本体の動きを判定。動いていれば起床
- P0 を1回サンプリングし、役に応じた判定 (触感: 参照値からの低下、握り: baseline からの上昇) に掛かれば起床
- ラジオを 100ms listen してペア起床ビーコンを確認

これにより、触感キューブはピン刺しで、握りキューブは握りで、いずれも最大1秒で起床する。

active 時間が1秒あたり 100ms 程度に収まるので、平均消費電流は約 1.5mA。単3×3 で idle 約68日を見込む。

### ペア起床ビーコン

ローカル入力で起きた側は 1.2秒間、50ms 間隔でビーコンを連投する。相手側は1秒周期の listen で必ず受信できる。クロック同期は不要。

ビーコンの中身は単なる「起きろ」信号ではなく、起床の原因となったペアイベント (`onPinStuck`・`onSqueezeStart` 等) そのものを乗せる。これにより、ビーコンを受けた側は wake すると同時に該当のイベントハンドラが発火する。片方を触ると相手も起きて、かつそのイベントを受け取れる体験が成立する。

ユーザーが片方を触ってから両方がアクティブになるまでの最大ラグは1秒。

### 出力の sleep 前後

スリープ突入時に拡張が次を強制する。

- cubeLight を Black に設定し PL9823 を消灯
- cubeVibe の PWM 出力を停止

内蔵デバイス (5x5 LED・スピーカー・マイク) は micro:bit ランタイムが deepSleep 中に自動で停止するため、拡張側では何もしない。micro:bit 基板の電源 LED も電池駆動時は deepSleep に連動して消灯する。

### wake 後の状態

deepSleep は RAM を保持するので、アプリ層の変数・登録済みハンドラ・cubePair の役宣言・グループ ID はそのまま維持される。アプリ層から見ると「実行が一時停止して再開した」だけに見える。

出力の状態は復元しない。cubeLight は Black、cubeVibe は停止のまま wake する。入力イベント駆動または forever ループで組まれたアプリは、wake 後に次の入力 or 次のループ反復で自然に追従する。「起動時に一度だけ set してずっと点けっぱなし」のような書き方は wake 後に色が失われるが、フィジェットのUXとして想定外なので許容する。

### ペア連動への影響

両キューブが同時に deepSleep に入っている状態では、双方ともラジオ受信を止めているのでペア通信は流れない。ただし片方がローカル入力で起きた瞬間に、起床の原因となったペアイベントがビーコンに乗って連投されるため、相手は次の周期 wake (最大1秒以内) でそれを受け取り、wake すると同時にそのイベントが発火する。

両方がアクティブになった後は、通常のペア間連動 (イベント自動配信・ポーリングのリクエスト/レスポンス) がそのまま動く。

## namespace 構成

出力 (発光・振動) は両キューブで完全共通、入力 (上面判定・ピン刺し・圧力) はキューブ固有とする対称構造を取る。共通プリフィックス `cube` を全 namespace に付け、子供がブロックパレット上でこの拡張のブロックをひとまとまりとして認識できるようにする。色相を散らして5 namespace を視覚的に区別する。`mood` のような意味付け語は採用せず、ハードウェア役割をそのまま名前にする。

- 触感キューブの入力 (`cubeTouch`): 色 `#FF8C42` (オレンジ)、アイコン `fa-hand-pointer-o`
- 握りキューブの入力 (`cubeGrip`): 色 `#E63946` (赤)、アイコン `fa-hand-rock-o`
- 発光 (`cubeLight`): 色 `#FFD23F` (黄)、アイコン `fa-lightbulb-o`
- 振動 (`cubeVibe`): 色 `#6A4C93` (紫)、アイコン `fa-bell`
- ペア連動の制御 (`cubePair`): 色 `#2A9D8F` (青緑)、アイコン `fa-link`
